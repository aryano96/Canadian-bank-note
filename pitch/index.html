Mint Rush · Backend: RNG and security

5

The question every player has is whether the game is rigged. Bank notes have security features so you can check they’re real, and Mint Rush works the same way. Before you bet, we show you a hash of the server’s seed. After the round we reveal the seed, and the Verify button recomputes the crash point right here in your browser with Web Crypto, using the same engine code the server runs. You can change your client seed at any time, so we can’t pick the result after you bet. Demo: open My bets, press Verify, and show both checks passing.

Return to player

99%

for every cash-out strategy. Cautious or greedy, the expected return is the same.

P(crash ≥ t) = 0.99 / t → t × 0.99 / t = 0.99

Mint Rush · Backend: game logic

6

Here’s why it’s fair mathematically. The house edge is 1%, so for any target t the chance of reaching it is 0.99 divided by t. Multiply by the payout t and you get 99% every time. No strategy beats another. The Stats tab simulates 200,000 rounds live to prove it, and if you change the house edge in config, the simulated return follows. The crash point is capped at 1000×.

Built like real money is on the line

Never charged twice

Every bet, cash-out and deposit carries an idempotency key. A retry returns the original result.

Server owns the money

Balances live on the server, one wallet per currency, with a ledger row for every change.

Server owns the clock

Cash-outs are priced by server time, so the browser can’t lie about timing.

All or nothing

Each money move runs in a SQLite transaction, in integer units down to 8-decimal Bitcoin.

Live and recoverable

Rounds stream over server-sent events, and a restart settles any round left running.

64 automated tests

Engine, economy and API, run against both the in-memory and the SQLite store.

Also: Zod validation on every route, rate limiting, hashed session tokens, errors that never leak internals.

Mint Rush · Backend: accounts, security, reliability

7

Underneath is a real backend. The server owns every balance and keeps a full ledger. Bets and cash-outs are idempotent, so a double-click or a dropped connection can never charge you twice, and there’s a test for exactly that. The server uses its own clock for cash-outs. Every money move is a database transaction, and amounts are integers in the smallest unit, so there’s no floating-point rounding. Rounds stream to the browser over server-sent events, and if the server crashes mid-round, it settles that round on restart from the stored start time and the committed crash point. Keep a terminal ready with npm test for the idempotency question.

Three parts, one rulebook

packages/engine

Pure rules

Provably fair RNG and game math, no I/O. The server and the in-browser verifier run the same code.

apps/server

Fastify API

Node 22 and SQLite behind a store interface, so Postgres could swap in without touching the rules.

apps/web

React and canvas

Vite, canvas lanterns, Web Audio sound, and a browser-only build on GitHub Pages.

config/game.config.json

One file drives the house edge, curve speed, limits, currencies, bonus rounds and simulated players.

Mint Rush · Modularity and configurability

8

It’s a TypeScript monorepo in three parts. The engine is pure game rules with no I/O, which is why the browser can verify a round with exactly the code the server used. The server is Fastify on Node 22 with SQLite, and the store sits behind an interface with in-memory and SQLite versions. The web app is React with the lanterns drawn on canvas. Every rule lives in one config file, so changing the game never means changing code.

What building it taught us

Clear beats clever

Our first version stamped crashes “Counterfeit” on an engraved graph. It looked great but read slowly, so we moved to plain stamps and lanterns.

Never trust the browser

If the browser said when it cashed out, a player could cheat. The server prices every cash-out from its own clock.

Config is a feature

Four new currencies, a faster curve and simulated players were mostly config changes, not code.

Show, then build

A mockup before each big change saved us from building the wrong thing more than once.

Mint Rush

11

A few things we learned. A clever theme has to stay readable: Counterfeit was fun, but Crashed was clear, and in a fast game clear wins. Never trust the client with money or time. A good config file is a feature in itself. And drawing a mockup before each big change, like the move from a graph to lanterns, kept us from building the wrong thing.
